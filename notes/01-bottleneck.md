# 01 · 怎么定位瓶颈

> 这个文件是方法，不是结论。以后换成 GEMM、Attention、任何 kernel，都从这里开始。

---

## 一、能卡住你的只有四堵墙

| 墙 | 本质 | 典型症状 |
|---|---|---|
| **带宽墙** | 数据搬不进来 | 实测带宽接近峰值，再改也没用 |
| **算力墙** | 某项计算太贵 | 带宽用不满，但 SM 一直在忙 |
| **延迟墙** | 并行度不够，请求排不满 | 带宽和算力都不满，SM 有大量空闲 |
| **开销墙** | 规模太小，启动/同步占主导 | 时间不随数据量线性增长 |

两个要点：

1. **四堵墙互斥**，任何一个 kernel 在任一时刻只撞其中一堵。
2. **优化不是拆墙，是换墙。** 每解决一个瓶颈，另一个就浮上来。所以"改完了反而更慢"是正常现象，不是失败。

## 二、动手前先算理论下限

不先算这个，就不知道自己在追什么。四步：

**1. 算必须搬运的字节数**

```text
bytes = 读一遍 + 写一遍 = 2 × M × N × 4
```

**2. 算带宽下限**

```text
t_mem = bytes ÷ 峰值带宽
```

**3. 算必须做的计算量**

```text
t_compute = (操作次数 × 每条操作的指令数) ÷ (SM 数 × 128 lane × 时钟)
```

本机参数（RTX 5070）：

```text
峰值带宽     672 GB/s
FP32 lane    48 SM × 128 = 6144 lane
时钟         ~2.5 GHz
指令吞吐     6144 × 2.5e9 ≈ 15.4e12 lane-指令/s
```

**4. 取大的那个作为下限，实测 ÷ 下限 = 效率**

### 实例：softmax v1，8192 × 8192

```text
元素数     = 67.1e6
bytes      = 2 × 67.1e6 × 4 = 536.9 MB
t_mem      = 536.9 MB ÷ 672 GB/s      = 0.80 ms
exp 次数   = 67.1e6 × 2（v1 算两遍）  = 134e6
t_compute  = 134e6 × 15 ÷ 15.4e12     ≈ 0.13 ms
```

```text
内存 0.80 ms ≫ 计算 0.13 ms  →  内存受限，比值 6:1
实测 0.986 ms ÷ 0.80 ms = 81%  →  已经贴着带宽墙
```

**这步最大的用处：它能直接否掉错误的优化承诺。**
有人说"改 online softmax 能快一倍"——算一下就知道不可能，那会突破物理下限。

## 三、分辨四堵墙：消融实验

理论下限只回答"能不能到"，不回答"差在哪"。差在哪得靠**一次只改一个变量**。

| 实验 | 怎么改 | 变快说明撞的是 |
|---|---|---|
| 去掉 exp | `expf(x-m)` → `x*0.5f` | 算力墙（SFU） |
| 只读不写 | 去掉第三遍 | 带宽墙 |
| 只跑一遍 | 注释掉第 2、3 遍 | 纯读带宽 |
| block 加大 | 256 → 512 → 1024 | 延迟墙 / occupancy 不足 |
| 单 block | `<<<1, 256>>>` | 开销墙 / 调度 |
| 限制寄存器 | `__launch_bounds__` | 寄存器压力压低了 occupancy |

**核心纪律：一次只改一个。** 同时改两个，测出来的数字解释不了。

## 四、流程

```text
1. 算理论下限（bytes/带宽 和 ops/算力）
2. 实测 ÷ 下限 = 效率
3. 效率 > 80%  → 贴着墙了，除非改算法，否则别再优化
4. 效率 < 80%  → 用消融实验定位是哪堵墙
5. 定位了再动手，一次一个变量
6. 改完回到第 2 步：变快了吗？换墙了吗？
```

**什么时候上 profiler（ncu）：**

- 怀疑是延迟墙，但不知道是哪个内存层级
- 算出的下限和实测差两倍以上，完全不知道差在哪
- 已经猜到了瓶颈，需要证据说服别人

**别让 profiler 代替思考。** 第一次跑会吐出上百个指标，没有假设的人会在里面迷路。

## 五、本轮实测记录（softmax v1，朴素三遍扫）

| M | N | 工作集 | 时间 | 有效带宽 | %峰值 |
|---|---|---|---|---|---|
| 512 | 128 | 0.5 MB | 0.0093 ms | — | — |
| 512 | 8192 | 32 MB | 0.0233 ms | — | — |
| 2048 | 8192 | 134 MB | 0.2387 ms | 562 GB/s | 84% |
| 8192 | 8192 | 536 MB | 0.9857 ms | 545 GB/s | 81% |
| 8192 | 128 | 8 MB | 0.0665 ms | 126 GB/s | 19% |

### 已经确认的三条

1. **第一版的 `%spec` 出现 >100%，是我算错了分母。**
   小工作集整个装进 L2，测的是 L2 不是显存。

2. **"读三遍 = 3 倍流量"是错的，L2 把重复读吸收了。**
   真实流量是 2 次访问。所以我预言的"online softmax 省一半带宽"，**实测收益接近 0**。
   → 记录：*预测 2 倍收益，实测约 0 倍，原因是 L2。*

3. **长行和短行是两个不同的问题。**
   `8192×8192` 撞带宽墙（81%），`8192×128` 撞开销墙（19%，24 次 `__syncthreads` + 一半线程空转）。
   **对短行做向量化没有意义，那是给带宽墙开的药。**

### 顺带澄清的两个概念错误

- **减最大值不是优化，是正确性。** 不减就 `inf/nan`。softmax 平移不变，这一步不改结果，只改"能不能算出来"。
- **`__syncthreads()` 不是对齐，是同步/屏障。** 对齐（alignment）说的是内存地址。

## 七、一条元规则

**算不出来就说明模型错了，不是代码错了。**

第一轮最大的收获不是数字，是体验到"我的模型是错的"——这比跑出一个好看的数字值钱。
