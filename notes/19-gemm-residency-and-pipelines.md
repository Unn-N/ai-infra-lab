# 19 · 驻留容量、数据停留与计算管线不是同一个上限

2026-11-07。用户质疑：DRAM 吞吐较低是否意味着计算算力已满？shared 数据停留时间是否是主要问题？64/4 单缓冲能否一次驻留下全部 block？

对象仍为默认 gemm_self_re.cu：OUTPUT_TILE=64、K_TILE=32、THREAD_TILE=4，(M,N,K)=(2048,2048,2048)。此次只观测，不改 kernel。

## 任务总量与同时驻留

输出 grid=32×32=1024 block，每块 256 线程。硬件 48 SM，当前理论最多 4 block/SM，因此全卡理论最多同时驻留 192 block。其余等待后续调度；不需要全部 block 同时驻留，前面执行结束释放资源后即可接后续 block，也不是必须整批结束才接下一批。

驻留位置紧张不等于计算流水满负荷。block 内线程等待、同步或执行其他指令时，寄存器/shared 配额仍被这个 block 占用。shared 中某份数据从加载到最后使用的生命周期可以跨越计算、读取、指令调度和等待，不能把“驻留时间”当作独立于这些活动的一个可相加耗时阶段。

## 实际限制 4 block/SM 的资源

查询报告给出：

| 项目 | 当前值 |
|---|---:|
| 每 SM 32 位寄存器 | 65536 个 |
| 编译器寄存器 / 线程 | 62 个 |
| 按分配粒度实际分配 / 线程 | 64 个 |
| 每 block 寄存器预算 | 64×256=16384 个 |
| 4 block 寄存器预算 | 65536 个 |
| 单按寄存器得到的 block/SM 上限 | 4 |
| 单按 shared 得到的 block/SM 上限 | 5 |
| 单按 warp 容量得到的 block/SM 上限 | 6 |

因此，这版 4 block/SM 的理论限制来自寄存器预算。不是因为每 SM 100 KiB shared 都被输入块填满；静态 shared 每块 16 KiB，实际分配还包含驱动保留部分。四块完全驻留时的寄存器预算用完，不代表每一时刻、每个 SM 都恰好驻留四块，更不代表寄存器或乘加单元每周期有效工作。

## 新补采的管线观测

沿用同一预热输入采集入口：跳过六次调用，采第七次；application replay、cache-control none、clock-control none；-O3 -lineinfo -arch=sm_120。把计算和 shared 指标分成两组，每组重复两次，减少不同计数器间的重放干扰。下面为两次范围。

| 指标 | 观测 |
|---|---:|
| 指令发射，elapsed 周期口径 | 71.89%—72.25% |
| FMA 管线指令吞吐 / 持续峰值 | 38.76%—38.96% |
| FMA 管线活跃指标，elapsed 口径 | 43.04%—43.25% |
| 实际 active warp 占用率，active 周期口径 | 63.06%—63.08% |
| L1TEX 汇总吞吐指标 | 77.89%—78.88% |
| shared load bank conflicts | 33596174—33601435 |
| shared store bank conflicts | 931024—932332 |

理论 active warp 占用率是 4×8/48=66.67%，观测约 63% 与这个容量约束相近。这个百分比统计在途 warp 数，不统计“有用计算的时间比例”。

FMA 指标与所有 SM 有效计算时间不是同一个量；其观测没有给出“乘加算力已经吃满”的证据。L1TEX 汇总吞吐取组成指标的较大者，不能称为“shared 带宽占用约 78%”；需要下钻其组成管线。确实观测到 shared bank conflicts，但原始次数不是时间损失比例，未通过布局对照隔离实际代价，因此不声称已证明 shared 是唯一瓶颈。

## 当前结论的边界

1. 1024 个 block 无法同时驻留在这张卡上，当前理论上最多 192 个。
2. 已明确触及的容量约束是每 SM 可分配寄存器预算，它限制驻留量；这与算术吞吐上限不同。
3. 之前预热 DRAM 字节带宽约 6%—7%，此次 FMA/发射/shared 观测支持继续检查 SM 内部数据供应与指令执行效率。仍不能仅凭 DRAM 低就给 kernel 贴上“计算算力受限”的结论。
4. “缩短数据驻留，才能提高带宽”需要进一步落实为具体操作：减少重复 shared 读取、减小依赖链、降低访存/控制指令或同步等待等。数据停留本身不是新增的一段工作，也不要求为了提高 DRAM 吞吐而降低复用。

当前未唯一确定主瓶颈，也未实现 padding、向量化或新的流水。原始结果、入口、精确命令、资源查询见 [data/2026-11-07-gemm-single64-limits](data/2026-11-07-gemm-single64-limits/)。二进制报告留在忽略的 build/single64_limits_2026-11-07/。
