# 06 · 一个 block 怎样算出一块 C

记录于 2026-11-06，整理自用户在 2026-11-05 至 2026-11-06 的推演。主题是**分块矩阵乘法的任务划分与计算流程**，尚未进入 register blocking 的实现。

## 计算目标

```text
A: M×K
B: K×N
C: M×N

C[i][j] = Σ A[i][k] × B[k][j]，k 从 0 到 K-1
```

开始计算前，A、B 已复制到 device 的 global memory，C 的输出空间也已分配在 global 中。

## 一块输出需要哪些输入

假设 A、B 都是 1024×1024，当前处理 C 左上角 32×32 的输出。

- A 需要前 32 行、全部 1024 列：一条 32×1024 横带。
- B 需要全部 1024 行、前 32 列：一条 1024×32 竖带。

横带来自 A，竖带来自 B。两条带包含这个输出块需要的全部输入，并不需要每个 block 都读取整个 A 和整个 B。

## 沿 K 分批计算

以每轮沿 K 取 32 个位置为例：

| 轮次 | 搬入 A 的位置 | 搬入 B 的位置 | 更新哪些输出 |
|---|---|---|---|
| 第 1 轮 | 行 0–31，列 0–31 | 行 0–31，列 0–31 | C 的左上角 32×32 |
| 第 2 轮 | 行 0–31，列 32–63 | 行 32–63，列 0–31 | 仍是同一块 C |
| 后续 | A 横带中继续向右 | B 竖带中继续向下 | 始终是同一块 C |
| 第 32 轮 | 行 0–31，列 992–1023 | 行 992–1023，列 0–31 | 完成同一块 C |

每一轮把对应的 A、B 输入块搬进这个 block 的 shared memory。所有参与线程把数据搬齐后再使用；所有线程用完这一轮的数据后，才能覆盖 shared、搬下一轮。

当前源码 `gemm/gemm_bench.cu` 的安排是一个线程负责一个输出元素，线程各自用 `float acc` 累加，通常由编译器放在寄存器中。每轮计算的贡献加进原来的 acc，不重置、不写回 C；K 方向的全部轮次完成后，才将最终值写到 C 对应位置。

```text
确定本次负责的 C 输出块
累加器清零
    搬入一对 A、B 输入块
    等待搬齐
    用这对输入块更新部分和
    等待大家用完
    换下一对输入块，继续累加
K 方向全部完成
写回这一块 C
```

## 两种“下一个块”要区分

1. **下一对 A、B 输入块**：还在计算同一块 C。保留累加器，继续累加。
2. **下一块 C 输出**：开始另一份输出任务。上一块写回后，换输出坐标，清零累加器，再处理新输出需要的输入。

当前源码让一个 block 处理一个 C 输出块，其他输出块交给其他 block。但这是一种代码安排，并非硬件规定。

用户提出的方案也成立：同一个 block 可以用外层循环依次处理多个 C 输出块。输入变大时，可以增加 block 数，也可以让一个 block 处理更多输出块，或者组合使用。具体性能需要之后比较。

GPU 也可以陆续执行大量 block，不要求所有 block 同时运行，因此不要求所有输出的部分和同时存在寄存器中。

## 已明确与尚未明确

### 坐标、加载与累加分别表示什么

在参考版本中，启动时使用 `block(TILE, TILE)`，一个 block 负责一个输出 tile，一个线程负责一个输出元素：

```cpp
tx = threadIdx.x;
ty = threadIdx.y;
row = blockIdx.y * TILE + ty;
col = blockIdx.x * TILE + tx;
```

- `tx / ty`：线程在 block 内的局部坐标。
- `row / col`：这个线程负责的输出元素在整个 C 中的坐标；此版本在 K 循环中保持不变。
- `K`：A 的列数、B 的行数，也是计算一个 C 元素需要遍历的乘加长度。
- `k0`：本轮输入 tile 在 K 方向的起点，每轮增加 `TILE`。
- 内层 `k`：本轮输入 tile 内的位置，取值从 0 到 `TILE - 1`。

对按行连续存放的矩阵，这一轮的加载关系是：

| 目标 shared 位置 | 原矩阵二维位置 | 一维地址偏移 |
|---|---|---|
| `As[ty][tx]` | `A[row][k0 + tx]` | `row * K + k0 + tx` |
| `Bs[ty][tx]` | `B[k0 + ty][col]` | `(k0 + ty) * N + col` |

每个线程各搬一个 A 元素、一个 B 元素；整个 block 合作填好两块输入 tile。越界的输入位置填 0，保持所有线程都参与两次 block 同步。

```cpp
// 输入搬齐并同步后，每个线程更新自己的输出累加器。
for (int k = 0; k < TILE; ++k) {
    acc += As[ty][k] * Bs[k][tx];
}
```

`acc` 在外层 K 循环之前初始化，逐轮保留部分和。外层循环结束时，各有效线程的 `acc` 才是最终输出值，随后写回 `C[row * N + col]`；边缘 block 用 `row < M && col < N` 判断哪些线程可以写回。

两次 `__syncthreads()` 的作用分别是等待输入搬齐，以及等待本轮数据被所有线程用完，避免下一轮过早覆盖 shared。同步应围绕实际的数据依赖判断，不能简单理解为“只要用了共享数据就到处加同步”。

### 这次纠正的重要认识

- block 是 kernel 启动时组织的线程组，不是固定拥有 1024 个线程的硬件部件。`dim3 block(x, y, z)` 描述逻辑形状，线程总数为三者乘积；1024 是当前设备常见的每 block 线程数上限，具体限制应查询设备。
- 线程、block 的编程组织需要映射到硬件执行。普通 block 由一个 SM 执行，同一 SM 能否同时容纳多个 block 取决于线程、寄存器、shared 等资源；大量 block 可以陆续执行。
- `blockIdx` 在当前 block 的生命周期内固定。让同一个 block 计算多个输出 tile 时，要自己用循环更新输出 tile 坐标，并为新输出重置累加器。
- warp 是有硬件执行意义的 32 线程分组。现代 GPU 不能仅凭“同一个 warp”就省略程序所需的同步；跨线程交换寄存器值需要 shuffle 等明确操作。
- 线程的寄存器具有私有的编程语义，底层由 SM 的物理寄存器文件支持。“寄存器访问快”不意味着所有相关读写和计算都保证一个时钟周期完成。

### 两个暂时不必加入的细节

`#pragma unroll` 控制紧接着的循环展开。这里 `TILE` 是编译期常量，可把循环展开为多条乘加；仍由当前线程完成，并不把循环迭代分给更多线程。不加它也可以正确计算，编译器本身也可能自动展开；收益需要测量。

shared 数组的 `+1` padding 不是当前访问方式的必要条件：在 `block(32, 32)`、float 元素的这个参考版本中，同一 warp 的 `ty` 固定，`As[ty][k]` 是同地址广播，`Bs[k][tx]` 是连续位置访问。不能沿用原注释“去掉 +1 必然明显变慢”的结论。自写版先采用 `[TILE][TILE]`，没有进行 padding 性能对比。

参考：[NVIDIA CUDA 编程模型](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)、[shared memory 访问](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/#shared-memory)、[`#pragma unroll`](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html#pragma-unroll)。
