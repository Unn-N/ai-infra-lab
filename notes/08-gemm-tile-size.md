# 08 · 只改 TILE：32、16 与 64

2026-11-07，用户提出并授权实验，由 Codex 执行。保持同一份 kernel、输入、编译选项与测量入口，仅修改 `#define TILE`；计时口径见 [07-gemm-baseline.md](07-gemm-baseline.md)。

## 结果

首先在本次环境重测 32，再测 16、尝试 64；因最小矩阵有明显波动，再以 16 → 32 顺序复测一组。表中每个数字都是该次进程内三轮平均耗时的中位数，不是跨进程的整体中位数。

| M,N,K | 首次 32 / ms | 首次 16 / ms | 复测 32 / ms | 复测 16 / ms |
|---|---:|---:|---:|---:|
| (128, 128, 128) | 0.084645 | 0.007434 | 0.011406 | 0.014787 |
| (512, 512, 512) | 0.122190 | 0.102125 | 0.112925 | 0.100906 |
| (2048, 2048, 2048) | 6.604706 | 6.344840 | 6.579194 | 6.233275 |
| (128, 1024, 512) | 0.057870 | 0.053837 | 0.059238 | 0.054958 |
| (127, 513, 257) | 0.024317 | 0.019014 | 0.023907 | 0.018611 |


16 与 32 的五组抽样对照均通过。除最小矩阵外，其余四组在两次对照中都观察到 16 更快；复测中耗时分别减少约 10.6%、5.3%、7.2%、22.2%。这是本次重复缓冲区测量的结果，不当作其他输入与环境的固定收益。

`128³` 的进程间变化很大，甚至改变了 16/32 的快慢关系，因此不对这一行给出优化收益结论。也不能仅凭其余四行就证明瓶颈或断言 16 对所有输入最优。

## TILE=64：编译成功，启动失败

查询设备得到 `maxThreadsPerBlock=1024`，`maxThreadsDim=(1024,1024,64)`，`sharedMemPerBlock=49152` 字节。每维限制与线程总数限制必须同时满足。

当前代码使用 `block(TILE,TILE)`，所以 64 会申请一个 `64×64=4096` 线程的 block，超过总线程上限。实际编译成功，但首次启动后的 `cudaGetLastError()` 报 `invalid argument`，进程以状态 1 退出，未产生正确性或性能结果。不能把它列为“更慢”。

限制的是 block 的线程数，不是输出 tile 不能为 `64×64`。若让较少线程各计算多个输出元素，就能设计 64×64 输出 tile；这需要修改当前一线程一输出的映射，不属于本次“只改常量”的实验。

## 解释范围与当前文件状态

改成 16 同时改变了每 block 的线程数、shared 用量、block 数、K 迭代轮次、数据复用及 warp 内的访问布局。资源占用与调度等都可能参与结果，目前没有 profiler 或受控消融证据来分离原因。

实验后已逐字节恢复原始源码，当前仍为 `TILE=32`，保留能运行的基线，没有留下 4096 线程的非法配置。源码 SHA-256：`0306184a4d13de625b8262c9ed1bf1d0b4702025a8764f9e4707f64c3207eb39`。

完整原始数据与 64 的实际错误见 [实验日志](data/2026-11-07-gemm-tile-size.txt)。不同 TILE 的可执行文件留在忽略的 `build/gemm_self_bench_tile16`、`build/gemm_self_bench_tile32`、`build/gemm_self_bench_tile64`；最后一个仅用于复现失败。
