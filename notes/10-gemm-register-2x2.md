# 10 · 输出块仍为 32×32，每线程改算 2×2

2026-11-07。用户确认首先集中研究每线程 2×2 输出，block=16×16，保持输出块 32×32、K 分块 32。由 Codex 在 `gemm/gemm_self_re.cu` 实现，各部分标注 Codex 注释；原 `gemm_self.cu` 基线未修改。

## 改了什么

1. `THREAD_TILE` 从 1 改为 2；线程的输出起点乘以 THREAD_TILE，四个输出由私有 `acc[2][2]` 累加。
2. 搬运按 block 内一维线程编号分工，以 block 线程总数为步长遍历两个 shared 输入块；256 个线程各搬 4 个 A 元素、4 个 B 元素。
3. 每个 k 先取两个 A、两个 B 到线程私有数组，交叉更新四个累加器。保留每轮加载后、覆盖前的两次同步。
4. K 结束后逐个检查四个输出的边界并写回。
5. 移除初稿的单输出/方形加载限制，保留正尺寸和输出均分的编译检查。本轮仅验证 32/32/2 配置，不据此声称其他配置均验证。

这是整项寄存器分块改动的对照：包含线程组缩小、协同加载和线程内复用的共同影响。输出 tile、K 轮数、全局输入块大小保持相同，没有加入双缓冲、向量化或 Tensor Core。

## 正确性

手算 2×3 乘 3×2 通过；CPU 全输出对照的 `(M,N,K)=(1,1,1)、(32,32,32)、(37,45,67)、(64,33,96)` 全部通过。前述全输出测试使用可精确表示的小数。

此外，相同性能输入中的随机正负 FP32 数据，在所有六次进程中、全部五组形状的 64 点 CPU double 抽样检查均通过，容差沿用原测量入口。抽查不代表全面正确性证明。

## 编译资源查询

```text
single: threads/block=1024 registers/thread=38 shared/block=8192 local/thread=0 theoreticalBlocks/SM=1
reg2x2: threads/block=256 registers/thread=42 shared/block=8192 local/thread=0 theoreticalBlocks/SM=5
```

同一 GPU 上理论可驻留 block 数由 1 变成 5，寄存器从 38 增至 42 个/线程；两者 shared 均为 8192 字节，查询到的 local memory 为 0。理论驻留能力不是测得的实际利用率，也不能据此把整个加速归因于驻留数量或单一层级带宽。

新版对每个 k 复用 2 个 A 和 2 个 B，完成 4 次乘加；与四个单输出线程各读取一对操作数相比，源码层面的 shared 操作数读取减少。但真实 shared 事务、广播、指令与等待时间的贡献仍需后续证据，不在本轮声称已经分离。
