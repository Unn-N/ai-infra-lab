# 02 · 执行模型 & 短行为什么慢

> 承接 01。01 讲“怎么定位瓶颈”，这篇讲“跑一个 kernel 时到底发生了什么”。

---

## 一、硬件层级

```
显卡
└── 48 个 SM
    └── 每个 SM 4 个分区
        └── 每个分区若干个 warp（调度单位）
            └── 1 个 warp = 32 线程（锁步执行）
```

代码侧的层级：

```
grid（8192 个 block）
└── block（256 线程 = 8 warp）
    └── warp（32 线程）
```

**`<<<8192, 256>>>` 不是 8192 个 block 同时跑。** 一个 SM 手上只有 6–8 个，跑完领下一批。
真正同时在飞的线程 ≈ 48 × 2048 ≈ 10 万，不是 200 万。

---

## 二、存储五级

| 层级 | 位置 | 延迟（量级） | 谁能访问 |
|---|---|---|---|
| 寄存器 | 线程私有 | ~1 周期 | 只有自己 |
| shared memory | 片上，每 block 一块 | ~20–30 周期 | 同 block 所有线程 |
| L1 | 片上，每 SM | ~30–40 周期 | 该 SM 所有 block |
| L2 | 片上，全卡共享 | ~150–250 周期 | 全部 |
| 显存 | 卡外 | **~400–800 周期** | 全部 |

**数字只记量级就够，关键是“显存慢两个数量级”。** 所以问题从来不是“慢不慢”，是“等不等”。

---

## 三、一次 kernel 的时间线（M=8192, N=128）

1. **启动**：8192 个 block 进队列，SM 分批领取。
2. **分工**（零访存）：`row = blockIdx.x`，`xr = x + row*128`，纯寄存器运算。
3. **第 1 遍求 max**：
   - 只有 warp 0–3（线程 0–127）进得去循环，warp 4–7 一次都不进
   - 每个 warp 发 1 条合并请求（32 线程 × 4B = 128B）
   - 然后阻塞 ~600 周期
4. **归约**：写 shared → 9 次 barrier（1 次 + 8 步树形）→ 得到全局 max
5. **第 2 遍**：再读 x（此次命中 L1，因为 512B 的一行还在），算 exp，累加
6. **归约**：再 9 次 barrier；两个归约合计 **18 次**
7. **第 3 遍**：再读 x（L1 命中），算 exp，写 y
8. **写回是异步的**：写进 L1 标记为脏，稍后才刷到 L2/显存。
   **所以计时必须同步，否则测的是“发射时间”不是“完成时间”。**

## 四、三个“为什么”

### 1. 为什么 warp 内不需要 `__syncthreads`？

warp 的 32 个线程锁步执行——同一条指令，32 个 lane 一起走，天然同步。
所以 `__shfl_down_sync` 可以在**寄存器之间**直接传值，不经过任何内存、不需要等人站队。

**一个 warp 处理一行 → 18 次 barrier 变 0。**

### 2. 为什么延迟要靠“更多 warp”来藏？

一个 warp 发 load 后阻塞 600 周期，调度器会切到别的就绪 warp。
**关键指标是“同时有多少 warp 就绪”，不是“有多少线程”。**

短行里 8 个 warp：4 个在等内存，4 个在等 barrier → 可用来藏的几乎为零。

### 3. 为什么加线程救不了短行？

`N=128` 把 block 从 256 加到 512：空转线程从 128 变 384，barrier 要等的人更多 → 更慢。
**方向是“让每个线程多干活”，不是“加更多线程”。**

## 五、二元模型：这是本文最有用的东西

```text
总时间 ≈ 每块固定成本 × block 数  +  数据量 ÷ 带宽
          └──── 与 N 无关 ────┘      └── 与 N 成正比 ──┘
```

**固定成本包括**：block 调度、block 启动/收尾、18 次 barrier、三次内存往返的延迟暴露。

实测验证（`M=8192`，旧版数据，无 L2 flush）：

| N | 数据量 | 时间 | 相对上一档 |
|---|---|---|---|
| 128 | 8.4 MB | 0.0665 ms | — |
| 512 | 33.6 MB | 0.0686 ms | **4× 数据，1.03× 时间** |
| 2048 | 134 MB | 0.2380 ms | 4× 数据，3.47× 时间 |
| 8192 | 537 MB | 0.9857 ms | 4× 数据，4.14× 时间 |

**转折点在 N=512 ~ 2048 之间**：从“固定成本支配”切到“带宽支配”。

### 两条推论

1. **“短行慢”不是“耗时长”，是“离理论下限远”。**
   `8192×128` 比 `8192×8192` 快了 14 倍，但数据量差了 64 倍。
2. **行做长是划算的（摊薄固定成本），做短是不划算的（摊不开）。**
   遇到短行的正解往往不是“优化这一行”，而是**把多行拼给一个 block**，摊薄固定成本。

### 由此得到的设计规则

> **每个线程手里应该有 4–8 个元素。**
>
> - 太少（1 个）→ 并行度浪费、请求数不够、循环展开失效
> - 太多（256 个）→ 单线程串行太久，同样喂不饱

`N=8192` + 256 线程 = 32 元素/线程（偏多但还行）
`N=128` + 256 线程 = 0.5 元素/线程（严重不足）
`N=128` + 32 线程（一个 warp）= 4 元素/线程 ✓ 甜区

## 六、测量经验（本轮新增）

| 观察 | 结论 |
|---|---|
| 同进程跑三次：573.7 / 574.8 / 573.9 GB/s | 抖动 0.1%，**同一次运行内可信** |
| 隔一次会话：0.9857 → 0.9340 ms（81% → 85.5%） | 跨时间漂移 5.5%，**基线必须现跑** |

所以：**同一张表里的横向对比可信，跨天的纵向对比不可信。**

---

## 七、exp 消融的结论

三个版本（`expf` / `__expf` / 纯乘法）在 `8192×8192` 上时间基本相同，乘法版甚至略慢。

> **计算不在关键路径上 → 不是算力墙，是带宽墙。**

我手算“exp 占 13%、能快 5–15%”是错的。**教训：手算的占比只能是假设，必须用消融验证。**
