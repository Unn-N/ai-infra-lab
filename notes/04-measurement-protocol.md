# 04 · 测量协议

> 2026-11-03 建立，当天升级两次。**在此之前所有"快了几个点"的结论都可能低于噪声。**

---

## 一、问题：噪声比优化幅度还大

同一份代码、同一台机器、隔几分钟跑两次：

| 尺寸 | 跑 A | 跑 B | 差 |
|---|---|---|---|
| `8192×512` | 72.9% | 91.5% | **19 个点** |
| `2048×2048` | 95.4% | 79.1% | **16 个点** |

这台 5070 同时在干两件事：跑 kernel、**渲染 Windows 桌面**。两者抢显存带宽。

## 二、协议

### 步骤

| | 动作 |
|---|---|
| 1 | 关 **Wallpaper Engine** 等动态壁纸（持续渲染，最凶） |
| 2 | 关任何 GPU 加速程序（MAA、安卓模拟器、浏览器视频） |
| 3 | 测的时候别动鼠标、别切窗口 |
| 4 | **每个配置跑 3 次，取中位数** |

### 为什么必须取中位数

做完 1–3 之后，噪声确实降了（15–19 点 → 1–2 点），**但没降到 0**。

第一次升级后仍然出现过：

```
标量 512×512 : 18.9 / 41.8 / 41.7      ← 18.9 是离群
标量 512×8192: 97.6 / 78.8 / 97.6      ← 78.8 是离群
```

**即使完全不操作电脑，单次测量仍会有 10–20 点的离群值。** 这是 WSL + 桌面合成这条链的噪声下限，关不掉。

> **单次数字永远不能用。三次取中位数是底线。**

## 三、另一个坑：`%spec` 会超过 100%

`512×8192` 的 float4 版，三次测出来 **101.9 / 101.0 / 100.4**——稳定超过理论上限。

**这不是变快了，是分母算多了。**

我们的带宽口径是“读一遍 + 写一遍”。但 16.8MB 的张量能整个装进 L2（约 40MB），写回被缓存吸收，**实际 DRAM 流量少于假设值**。

**判据：`%spec` 超过 95% 就要怀疑，超过 100% 说明这个尺寸不能用这个口径。**

## 四、什么时候能信

| 用途 | 能不能用现在的 bench |
|---|---|
| 判断 5 倍级别的改动（19% → 93%） | ✅ 能 |
| 判断 5–10% 的改动（`float4`、调参） | ⚠️ 要做 3 次中位数 |
| 判断 3% 以内的改动 | ❌ 不能，需要上 profiler 或固定时钟 |

## 五、一条通用教训

> **测量的可信度，是你所有优化结论的上限。**

噪声 15% 的测量工具配上再聪明的优化思路，也只能得出随机结论。**“先把测量搞稳”永远排在“先优化”前面。**

`notes/01` 里那句"性能优化需要一套可靠的工作方法"是对的，但那一版漏了最关键的一条：

> **环境本身也是测量的一部分。**
