# 21 · 仅给 As 加一列：冲突减少，但加载指令变多

2026-11-07。用户讨论 bank 分布这一硬件细节后同意尝试 padding。选当前最快的 64/4 单缓冲，OUTPUT_TILE=64、K_TILE=32、THREAD_TILE=4、block=16×16 不变。此次只将 As[64][32] 改为 As[64][33]，Bs[32][64] 不变；不改变有效加载、乘加顺序或输出。中断前完成正确性与普通性能计时，恢复后继续采集计数器与反汇编。

## 假设与资源

第一个 warp 的两组16线程分别读取 As[i][k] 与 As[4+i][k]。按32位标量访问看，行跨度32会让两个不同地址落同一 bank；跨度33使它们的 bank 相差4。预测可减少这类读取冲突，但编译器的向量加载和对齐也可能受影响。

| 资源 | 原版 | As 加一列 |
|---|---:|---:|
| 静态 shared/block | 16384 B | 16640 B（增加256 B） |
| 寄存器/线程 | 62 | 56 |
| local/线程 | 0 | 0 |
| 理论 block/SM | 4 | 4 |

## 正确性与普通性能对照

原版和候选均通过现有七组逐输出 CPU double 检查；两版三次进程、五组输入的全部64点性能抽查通过。未重新尝试受 WDDM 主机调试接口阻挡的 Compute Sanitizer，不声称通过竞争检测。

同一测量入口、相同输入与随机种子，编译 -O3 -lineinfo -arch=sm_120；每进程预热5次、3轮各20次，CUDA events，不计分配/拷贝/校验，相同缓冲不清 L2。进程顺序 baseline、padA、padA、baseline、baseline、padA；表中取九轮批量平均耗时的中位数。

| M, N, K | 原版 ms | 仅 As 加一列 ms | 加速比：原 / 新 |
|---|---:|---:|---:|
| 128, 128, 128 | 0.011022 | 0.012680 | 0.869× |
| 512, 512, 512 | 0.043642 | 0.046269 | 0.943× |
| 2048, 2048, 2048 | 1.566336 | 1.718776 | 0.911× |
| 128, 1024, 512 | 0.033741 | 0.047306 | 0.713× |
| 127, 513, 257 | 0.027120 | 0.023184 | 1.170× |

2048方阵从 **1.566336 ms** 增到 **1.718776 ms**，耗时约增加 9.7%。三次进程中位数均为候选更慢。512方阵和128×1024×512长方形也出现回退；最短任务和非整齐边缘输入波动较大，最后一组不作稳定加速结论。

## 2048输入的计数器对照

分别给两版编译独立采集入口，相同随机输入序列与预热：先执行6次，采第7次。Nsight Compute application replay、cache-control none、clock-control none。两轮反向顺序；原始CSV与精确命令均保留。profiler耗时不替代上方普通计时。

| 指标 | 原版 | As 加一列 |
|---|---:|---:|
| shared 读取 bank conflicts | 33,598,448—33,601,062 | 30,949—35,436 |
| shared 写入 bank conflicts | 945,165—946,269 | 808,387—819,096 |
| 动态 shared 加载指令（warp 指令） | 50,331,648—50,331,648 | 67,108,864—67,108,864 |
| 动态 shared 存储指令（warp 指令） | 8,388,608—8,388,608 | 8,388,608—8,388,608 |
| shared load wavefronts | 134,261,744—134,264,358 | 117,471,461—117,475,948 |

shared 读取冲突减少约99.9%，所以 padding 在减少这一类访问冲突上确实有效。但动态 shared 加载 warp 指令从50,331,648增加到67,108,864，恰好增加约33.3%；存储指令数不变。shared load wavefront总量下降约12.5%，说明不能把 wavefront、冲突次数和指令条数当成同一个量。

## 生成代码揭示的代价

计算循环的静态 shared 读取指令：

| 指令 | 原版 | As 加一列 |
|---|---:|---:|
| LDS.64（每线程读两个float） | 4条 | 2条 |
| LDS（每线程读一个float） | 0条 | 4条 |
| LDS.128（每线程读四个float） | 2条 | 2条 |
| 合计 | 6条 | 8条 |

反汇编中 A 的行偏移由0、0x80、0x100、0x180变为0、0x84、0x108、0x18c。33个float一行是132字节，奇数行的起点不再8字节对齐；原有其中两条64位读取拆成四条32位读取。动态计数与静态6→8的变化一致。Bs仍保留128位读取。

因此现在有具体证据：As加一列改变了bank映射、消除了大部分shared读取冲突，同时也改变了对齐和编译后的加载指令数量。候选在普通计时中总体回退，不能只凭冲突下降就断言会加速。寄存器数也变化，尚未隔离全部代码生成效应，不能将整段回退百分比全部归给新增两条加载指令。

## 当前状态与复现

默认 gemm/gemm_self_re.cu 保持未padding的64/4单缓冲，没有用回退的候选覆盖它；独立双缓冲文件也未改动。候选与原版可执行文件保留于 build/padding_as_2026-11-07/{baseline,padA}/。

原始数据、两版实际编译源码、采集入口、资源、编译输出及反汇编见 [data/2026-11-07-gemm-padding-as](data/2026-11-07-gemm-padding-as/)。复现时将对应 baseline_gemm_self_re.cu.txt 或 padA_gemm_self_re.cu.txt 放入单独目录并命名 gemm_self_re.cu，再把共同 gemm_self_bench.cu.txt 去掉.txt放到同目录，按原编译参数运行。当前没有继续试+2、Bs padding、swizzle或其他布局。

这次识别的两个硬件约束是：bank分布，以及访问对齐/向量加载。记录尚未提交或push。
